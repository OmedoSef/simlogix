# SimLogix

> This file is the project's reference guide. It must be **updated on every new decision** (architecture, scope, convention) to stay the source of truth — including when switching machines.

Project name: **SimLogix** (Sim + Logic).

## Project context

Romain wants to replace Logisim with a tool that fixes his main frustrations:

- **Tedious canvas interaction**: placing/wiring gates and wires is slow and clunky.
- **Painful component appearance editing**: Logisim's shape editor is limited.
- **Poorly handled feedback loops**: circuits with combinational feedback (e.g. an SR latch in NAND) cause bugs/hangs in the simulation engine.
- **Dated UI/UX** (Swing/Java).

Goal: a cross-platform logic simulator, written in Rust.

## Architecture decisions

_(these are the decisions and their rationale; see Progress for what is actually built)_

- **2-crate Cargo workspace**:
  - `simlogix-core/` — circuit model + simulation engine, no GUI dependency, testable in isolation.
  - `simlogix-gui/` — schematic editor + rendering + real-time simulation loop.
- **GUI: egui / eframe.** Chosen over iced or Slint for direct control of the `Painter` (smooth custom rendering of gates/wires/grid) and the immediate mode which naturally fits a real-time simulation. Native cross-platform + WASM export possible later.
- **Simulation engine: discrete events with propagation delay.** This is the answer to the feedback-loop problem. Every component has a propagation delay (defaults to 1 logical tick); an input change schedules an output event at `t + delay` instead of propagating instantly. An event queue ordered by logical time processes events in order — like HDL simulators (Verilog). This avoids infinite recursion on a combinational loop by construction (an SR-NAND latch or ring oscillator converges/oscillates instead of crashing).
  - Oscillation detection: if a net changes state more than N times within the same time step, the engine stops and reports "unstable circuit" instead of freezing the UI.
- **Data model**:
  - `Signal::{High, Low, Unknown, Error, HighZ}` — the unknown/error state is planned from the start (one of the "simulation bug" irritants often comes from mishandling X/Z). `HighZ` is distinct from `Unknown`: `Unknown` means "not driven / not simulated yet", `HighZ` means "this specific driver is deliberately not driving right now" (tri-state).
  - `Pin`: input, output, or bidirectional (`PinDirection::InOut`) terminal of a component, connected to a `Net`.
  - `Component`: a trait with `eval(&self, inputs) -> outputs` + `propagation_delay()`. Sub-circuits also implement this trait (hierarchy is a first-class citizen, not a hack).
  - `Circuit`: graph of components + nets, event queue, logical clock.
  - **Multi-driver nets** (implemented — `Circuit::resolve`): a net can have more than one potential driver, which is what a bidirectional/tri-state buffer needs. Resolution rule when computing a net's `Signal`: ignore drivers reporting `HighZ`; if 0 remaining drivers → `Unknown`; if 1 → that driver's value; if ≥2 with differing values → `Error`. `Transistor` already relies on this by driving `HighZ` when it isn't conducting; no component exposes a true bidirectional pass yet.
- **Dev container** (`.devcontainer/`): `rust:1-slim-bookworm` image + X11/GL/GTK libs needed by eframe (`libx11-dev`, `libxkbcommon-dev`, `libgl1-mesa-dev`, `libgtk-3-dev`, etc.), `clippy`/`rustfmt` installed. The host's X11 socket (`/tmp/.X11-unix`) is mounted and `DISPLAY` propagated, so `cargo run` from the container opens the window directly on the host desktop (X11 forwarding). The host's D-Bus session socket (`${localEnv:XDG_RUNTIME_DIR}/bus`) is mounted the same way, with `DBUS_SESSION_BUS_ADDRESS` propagated — this lets `rfd`'s native file dialog (used for save/load) reach the host's real `xdg-desktop-portal` instead of needing a portal running inside the container (there isn't one). Tried forcing `rfd` onto its `gtk3` feature first as a workaround; reverted once the D-Bus forward worked, since `gtk3`'s gtk-rs bindings are unmaintained (`cargo audit` flagged them) and the portal is the more correct approach anyway. `remoteUser: vscode` to stay consistent with the pattern already used on `file-checker`. The container is only for the build/dev toolchain (source code is bind-mounted by VS Code, not copied into the image).
  - `cargo install cargo-audit`/`rustup component add` in the Dockerfile must run **after** switching to `USER vscode`, not before — running them as root first leaves root-owned files in the shared cargo registry cache that later block `vscode` from writing new entries (`Permission denied`). Learned this the hard way after a devcontainer rebuild.
  - `cargo build --release` inside the devcontainer produces a binary at `target/release/simlogix-gui` that also runs directly on the host (bind-mounted, so no copy needed) — the container's Debian bookworm has an older glibc (2.36) than a typical host, and glibc is forward-compatible, so this direction works. Confirmed working on the host's real Ubuntu 24.04 desktop, including the native save/load dialog (no forwarding needed there, since it's not sandboxed in a container).
  - Practical setup instructions (`xhost` prerequisite, how to open the devcontainer): see [README.md](README.md), not duplicated here.

## v1 scope / Out-of-scope

**In v1 (minimal simulator):**
- Basic gates: AND, OR, NOT, NAND, NOR, XOR, XNOR, buffer.
- Bidirectional/tri-state buffer (bus transceiver) — added to scope because Romain will need it; requires the multi-driver net resolution described above.
- Input (switch/button), output (LED), clock.
- Schematic editing: placement, wire routing with grid snapping and orthogonal routing, rotation, multi-select/move.
- Real-time simulation wired into the UI loop.
- Save/load a circuit (serde).

**Out of scope for v1 (future roadmap, not to be built now):**
- A full custom appearance *editor* (user-drawn symbols) — v1 ships hand-coded vector symbols per component kind instead (see the "Component appearance" convention below), not a UI for drawing your own. This is Romain's pain point #2; a real editor is addressed after the core is solid.
- Multi-bit buses, memory (RAM/ROM), VHDL/FPGA export, collaboration.

## Code conventions

- **Language**: identifiers (types/functions/variables) in English (standard Rust convention); comments and doc-comments (`///`, `//!`) also in English. `README.md` stays in French; `CLAUDE.md` is in English (switched from French on request, no functional reason — just consistency with the rest of the written material).
- **Error handling**: custom errors via an `enum` + [`thiserror`](https://docs.rs/thiserror) (no raw `String` errors, no `anyhow` in `simlogix-core` — it's a lib, callers need to be able to match on precise variants).
- **Panics**: `panic!`/`unwrap()`/`expect()` forbidden outside `#[cfg(test)]`. An invalid input or malformed circuit must always surface as a `Result`, never panic.
- **Formatting/linting**: `cargo fmt` (default config, no `rustfmt.toml`) and `cargo clippy` before considering a step done. No custom clippy config for now (may tighten later — `deny(warnings)`, `pedantic` — if needed).
- **Tests**: unit tests co-located in a `#[cfg(test)] mod tests` module at the bottom of the file they test, preceded by a banner comment separating it from the real code:
  ```rust
  // -----------------------------------------------------------------------------
  // Tests
  // -----------------------------------------------------------------------------

  #[cfg(test)]
  mod tests {
  ```
- **Module organization**: one file per concept — `signal.rs`, `pin.rs` (`Pin`, `PinDirection`), `net.rs` (`NetId`, later `Net`), `component.rs` (the `Component` trait only), `circuit.rs`. `lib.rs` stays just crate doc + `mod`/`pub use` declarations, nothing else. Once there are several concrete components (gates, `Button`, `Led`...), they go under a `components/` subfolder rather than piling into `component.rs`. Each file keeps its own `#[cfg(test)] mod tests` at the bottom.
  - Same principle applies to `simlogix-gui`: `main.rs` stays just `mod` declarations + `fn main()`. `app.rs` (`SimLogixApp`, the `eframe::App` loop), `canvas.rs` (grid + generic box/pins rendering, `BOX_SIZE`/`snap_to_grid`), `palette.rs` (`ComponentKind`, the palette panel), `placed_component.rs` (`PlacedComponent`: draw + interact for one placed instance).

- [x] **Feedback-loop tests** (`simlogix-core/tests/feedback.rs`) — the founding architectural claim, finally under test rather than only in prose.
  - **Integration tests, not unit ones**: they drive `Circuit` plus several concrete components through the public API alone, so there's no single file to co-locate them in. First use of `tests/` in this project; the co-location convention still stands for unit tests.
  - **The SR-NAND latch test turns on the *hold* case**: same inputs, opposite output depending on history. That's memory out of a purely combinational loop, which is exactly what an instantly-propagating engine can't produce — set, hold, reset, hold.
  - **A ring of plain inverters would have tested nothing.** `Not(Unknown)` is `Unknown`, so an undriven ring stays undriven forever and the test would have passed without ever oscillating; real silicon starts on noise, this needs a definite value put in deliberately. The ring is therefore `Nor` + 2 × `Not`, the `Nor` doubling as an enable that seeds it.
  - **A prediction of mine was wrong, and the engine is better than I claimed.** I expected the forbidden-state release (both active-low inputs asserted, then both released together) to oscillate and be reported as unstable. It settles: the tie is broken by the order the two gates happen to be evaluated in, landing on a legal complementary state — what Verilog-style simulators do. The test asserts it leaves the forbidden state, deliberately *not* which way it falls, since that's an implementation detail rather than a promise.
  - **`run()`'s known trade-off is now pinned by a test** rather than living only in prose: draining a healthy oscillator trips `MAX_TOGGLES_PER_NET`, because the toggle counter is per `advance()` call. The GUI uses `advance` in small steps for that reason.

- [x] `Clock` component (`components/clock.rs`) — a periodic source, alternating `Low`/`High` every evaluation. Required real engine changes, not just a new `Component` impl:
  - **`Circuit::schedule_periodic(component, period)`**: marks a component as self-rescheduling forever after every evaluation (`evaluate()` reschedules it at `clock + period` unconditionally, on top of the normal reader-rescheduling logic). Without this, a `Clock` would tick exactly once and go silent — it has no inputs, so nothing would naturally re-trigger it.
  - **`Circuit::advance(ticks)`**: processes events up through `clock + ticks`, then *stops* — unlike the old `run()` (drain until empty), which would never return once a periodic component exists, since the queue is never truly empty. `run()` still exists, now defined as `advance(MAX_RUN_TICKS)` (a large but finite bound: 1,000,000) purely so it can never hang — existing tests/call sites didn't need to change, but **`run()` is the wrong tool for a clocked circuit**: it can legitimately trip `MAX_TOGGLES_PER_NET` (a fast clock ticking that many times looks indistinguishable from genuine instability) and, worse from the GUI's side, it would let any placed clock burn through a huge chunk of its future ticks in one synchronous burst.
  - **GUI**: `SimLogixApp::ui()` now advances the circuit by real elapsed time *every frame* (`TICKS_PER_SECOND = 60`, accumulated via a fractional `tick_budget`) and calls `ctx().request_repaint()` unconditionally — this is what makes a placed `Clock` visibly tick at a real, wall-clock-tied rate (`CLOCK_PERIOD_TICKS = 60` → 1 toggle/second) instead of free-running as fast as the CPU allows. Tradeoff: the app now redraws continuously (higher idle CPU use) regardless of whether a `Clock` is present, not just on input, to keep this working. All the interactive-settle call sites (button press, wire connect/disconnect, project load) were switched from `run()` to `advance(SETTLE_TICKS)` (a small constant, 32) for the same reason — calling `run()` from *any* interaction would also burst-advance any clock elsewhere in the circuit.
- [x] Fixed a real pin-alignment bug found while testing the clock: multi-pin edges (e.g. a `Transistor`'s `G`/`S`) were positioned by fractional interpolation across the box's height, which doesn't land on the grid except by coincidence for exactly 1 pin. `canvas`'s pin-spacing helper now places each pin a whole multiple of `GRID_SPACING` from the box's center instead.
- [x] Settings menu: light/dark theme (defaults to OS theme via egui's `ThemePreference`/`Theme`), and a language picker (English/French/Italian, defaults to OS locale) — see the i18n convention below.
- [x] Palette reorganized by category (Sources/Outputs/Transistors), each entry showing an icon + name; the canvas now shows only the icon (see "Component appearance" convention below) — the previous auto-generated "box + named-pin-text" appearance is gone.
- [x] **Component appearance convention (standing decision)**: every component kind gets a hand-drawn vector symbol in `simlogix-gui/src/symbol.rs`, not a generic box. No enclosing box, no text labels (not even pin names) — a pin's exact position is wherever that symbol's own lead line ends, not an independently-computed generic offset; the symbol owns its `PinPositions`, returned from `symbol::draw`. A symbol is defined once in its canonical `Rotation::Deg0` layout; `symbol::rotate` rotates every point of it (geometry and pins together) for the other 3 rotations, so the icon and its pins always agree at every rotation instead of only the pins moving. `BOX_SIZE` (`canvas.rs`) is deliberately sized so its half-extents are whole multiples of `GRID_SPACING` — since a symbol's pins sit at the box's own edges/corners, this is what keeps every pin landing exactly on a grid dot. **Going forward, every new component gets a real symbol here by default** — falling back to placeholder/no-symbol rendering only if Romain explicitly asks for it, or if a sensible symbol genuinely doesn't exist yet for that kind.
- [x] **All 8 v1 logic gates**: `And`/`Or`/`Nand`/`Nor`/`Xor`/`Xnor`/`Not`/`Buffer` (`simlogix-core/src/components/`), each combinational (no internal state). 2-input gates resolve uncertain inputs by dominance (e.g. `And`: a definite `Low` on either input forces `Low` regardless of the other; short of that, `Error` dominates; short of that, anything but both definite is `Unknown`) — mirrored for `Or`/`Nand`/`Nor`. `Xor`/`Xnor` have no dominant input (either input alone still leaves the output dependent on the other), so both inputs must be definite to resolve; `Error` still dominates over plain uncertainty. `Not` inverts (`HighZ` and `Unknown` both resolve to `Unknown`); `Buffer` passes every signal state through unchanged. New "Gates" palette category. GUI-side, this is fully generic — adding a gate of the same shape needs no new `PlacedComponent` variant:
  - **2-input gates** (`PlacedComponent::TwoInputGate`, `placed_component.rs`): two inputs at pin index 0/1, one output at pin index 2 — same shape for `And`/`Or`/`Nand`/`Nor`/`Xor`/`Xnor`, added via `PlacedComponent::two_input_gate(id, center, kind)`.
  - **1-input gates** (`PlacedComponent::OneInputGate`): one input at pin index 0, one output at pin index 1 — `Not`/`Buffer`, via `PlacedComponent::one_input_gate(id, center, kind)`.
  - Symbols (`symbol.rs`) share drawing code within each shape family via an `invert: bool` (and `xor: bool` for the OR family) parameter, plus a shared `bubble_end` helper that draws the small inversion "bubble" and returns where the lead past it continues — `draw_and_gate(..., invert)` covers And/Nand, `draw_or_gate(..., xor, invert)` covers Or/Nor/Xor/Xnor, `draw_triangle_gate(..., invert)` covers Buffer/Not. Mirrors the existing `draw_transistor(..., is_n_type)` pattern.
  - Adding a genuinely new shape (a gate that doesn't fit either family) still follows the checklist: `ComponentKind` variant in `palette.rs` (+ its `category_gates` entry), a `component_xxx` label in `i18n.rs` (3 translations), a `draw_xxx` in `symbol.rs`, and a `place()` arm in `app.rs`.
- [x] **Multi-waypoint wire routing with explicit `Wire` objects**, replacing both the old drag-from-pin-release-on-pin gesture (single automatic bend) and, shortly after, the "infer topology from net membership" render model entirely. Wiring is click by click: click a pin to start a wire, click anywhere on the canvas to drop as many grid-snapped waypoints as wanted, click a pin — or an existing wire's waypoint, tapping into it as a junction — to finish (Escape cancels).
  - **`SimLogixApp.wires: Vec<Wire>`** is now the source of truth for both rendering and editing (`next_wire_id: u64` hands out stable ids, `selected_wire: Option<u64>` selects by id — no more `(NetId, usize)` keying, and with it the **known instability** that came from indexing into an arbitrary net-membership grouping is gone). A `Wire` has `net`, `from: (ComponentId, usize)` (every wire starts from a real pin), `to: WireEndpoint` (`Pin(ComponentId, usize)` or `Junction(Pos2)` — a fixed point tapping into another wire), and `waypoints: Vec<Pos2>`. `SimLogixApp.wiring_from: Option<WireInProgress>` (`from`, `net`, `anchor`, accumulated `waypoints`) tracks a wire mid-creation.
  - **Why the rewrite, not a patch**: the old model rendered each net as a "star" from an arbitrary anchor pin to every other pin sharing it, inferred fresh each frame from `Circuit` net membership. That has no way to represent a wire ending on a point that isn't a pin at all — which is exactly what a junction is — so bolting junctions onto it would merge the net correctly but render the new wire wrong (a fresh auto-routed line from an unrelated anchor, ignoring the path actually drawn to the junction).
  - **Junction endpoints track their host live** (fixed shortly after shipping the static version above, once Romain hit it in practice): `WireEndpoint::Junction { wire: u64, waypoint: usize }` references the host wire's id and which of its waypoints, not a frozen `Pos2` — so dragging that point (even the host's own implicit default-route point, which materializes into a real waypoint the moment it's first dragged) drags every tap on it along too. Resolved fresh every frame in a pre-pass (`ui()`, a `HashMap<u64, Resolved>` built by iterating `self.wires` in creation order) rather than recursively, since a wire can only tap into an *already-existing* — so already-resolved — earlier wire; that ordering guarantee is what makes a single forward sweep enough, no cycle handling needed. Deleting a wire cascades to anything junction-tapped onto it (and transitively onto *those*), so a delete never leaves an orphaned tap silently un-renderable and un-selectable; same cascade on deleting a component, since removing its wires has the same orphaning risk.
  - **Deletion**: disconnects whichever endpoint is a real pin uniquely belonging to that wire (`to` if it's a `Pin`, else `from`, since a `Junction` has no pin of its own) via `Circuit::disconnect_pin` — same "give this one pin a fresh net, everyone else stays connected" semantics as before, which turns out to generalize correctly to junctions without special-casing: deleting a tap wire only detaches its own pin; deleting a host wire only detaches its own far pin, leaving anything junction-tapped onto it (still on the same underlying net) unaffected. **Superseded** by the derived net model below: deleting a wire is now just removing it from the drawing, and no pin is detached by hand at all.
  - **Post-hoc reshaping**: every waypoint has its own visible dot and drag handle, snapped to grid on release; double-clicking a wire inserts one, right-clicking one removes it. (The automatic mid-wire Z-bend this originally materialised from has since been removed — see below.)
  - **Save/load** originally kept deriving wire *groups* from net membership, so shape and junctions weren't persisted. Superseded: the format now stores wires explicitly (see the project-format entry below).
  - **Deselection**: clicking empty canvas clears the selection (tracked by a per-frame `click_consumed` flag — set by anything selectable that claims the click: a component, a wire, a waypoint, a pin — so "hit nothing" is a real signal rather than a guess), and Escape/right-click backs out one step at a time: a wire in progress first, then, once there's none, the selection and any queued placement. Selecting a component and selecting a wire are also now mutually exclusive — `Delete` checks the wire first, so leaving a stale wire selected while clicking a component would have deleted the wire instead of the component just clicked.
  - **Fixed a real bug found immediately after shipping the click-based interaction**: a component's own drag/click area (its full box rect) overlapped every pin's hit-rect (pins sit exactly on the box's edge), and since the box's `ui.interact()` ran first, a click meant to start a wire on a pin could get claimed by the box instead and move the component. Fixed by insetting the box's interactive rect by `PIN_HIT_MARGIN` (`placed_component.rs`, half a pin's hit-rect size) so the two never overlap — drawing/symbol geometry is untouched, only the interactive area shrank.
  - **1-input gates** (`Not`/`Buffer`) needed their own `PlacedComponent::OneInputGate`, since they don't fit `TwoInputGate`'s shape. Both are done.

- [x] **Wires became first-class drawable objects**, in a sequence of steps that each removed a special case rather than adding one:
  - `WireEndpoint` is `Pin` | `Junction { wire, waypoint }` | `Free(Pos2)`, and **both** ends use it. Deleting a component therefore keeps its wires, cut loose where the pin was — the cost is asymmetric (deleting an unwanted wire is one click; redrawing a wanted one is not), and dragging a loose end onto the replacement is exactly how you swap a gate.
  - **Deleting no longer cascades.** It used to delete every wire tapped onto a deleted one, to stop an orphaned tap resolving to nothing and silently vanishing. That was deleting user data to hide a rendering bug; making the orphaned state representable (`Free`) was the actual fix.
  - **Junctions track their host live** (by wire id + waypoint index, resolved every frame) rather than freezing a position, so moving a contact point drags its taps along. Resolution iterates to a fixpoint instead of assuming creation order, which is what lets a wire be re-attached to *any* other one.
  - **Splitting and joining** are inverses: right-clicking a segment cuts it, and dropping two loose ends together rejoins them (`reverse_wire` first lines the two up, mirroring junction indices). A cut originally had to work out whether the pieces really ended up separate before detaching the far pin — a tap bridging the cut point keeps them joined. The derived net model below deleted that reasoning outright: cutting changes the drawing, the drawing is re-read, and a bridged cut simply comes back as the same group.
  - A wire is exactly the points it was given; the implicit mid-wire Z-bend is gone. For a level wire it produced *two* points at the same spot, which surfaced as a stray point on top of an end after a cut. Removing it also deleted the "phantom point that only becomes real once dragged" special case from three call sites.

- [x] **Geometric net model**: connectivity is now *derived from the drawing* after every edit, instead of being accumulated as wires are drawn. This is the model KiCad and Logisim use, and it closes the known limitation logged above — two separate wires between the same pins, one of them cut, stay connected.
  - **Why the previous model couldn't be patched**: a destructive merge doesn't remember *why* two pins ended up together. Once `merge_nets(a, b)` has run, nothing records whether one wire or three put them there, so `disconnect_pin` on a delete could only guess. Every fix built on it was a special case compensating for that missing information (does a tap bridge the cut? did the pieces really separate?) — the information simply wasn't there to consult.
  - **`Circuit::rewire(&[Vec<(ComponentId, usize)>])`** replaces `merge_nets`/`disconnect_pin` (both removed — keeping a second, contradictory way to manage connectivity is exactly how the two would drift apart). The caller owns the drawing and hands over the groups of pins it says are connected; `rewire` throws away the whole pin→net mapping and allocates one fresh net per group, plus one per pin no group mentions. Contributions already driven onto a net **follow their pin**, so nothing has to be re-evaluated to get the values back, and only components whose *inputs actually changed* are rescheduled — which is what keeps a `Clock` (no inputs, hence never disturbed) from having its phase reset on every unrelated edit.   - **GUI side, `SimLogixApp::rebuild_nets`**: union-find over `Node::{Pin, Wire}`, each wire unioning itself with whatever its two ends touch (a `Free` end contributes nothing), then every group holding more than one pin goes to `rewire`. A test asserts the thing that could have gone wrong: driving a net reschedules everything reading it, including this component, and it converges instead of re-triggering itself forever.
  - **The "a pin that reads the net it drives" question, answered rather than worked around.** Within one evaluation it can't bite: `Dir` picks read-`A`-drive-`B` or the reverse, and the pin being read is always the one driving `HighZ` — there's no echo to see. Across a *change* of direction there's one tick where the newly-read side still carries the previous contribution, because it's only withdrawn when the new outputs land. That's bus turnaround and it's physically real; a 74x245 glitches the same way if flipped while both sides drive.
  - **Having the engine hide a component's own contribution from it was the alternative, and it would be wrong.** An open-drain pin has to see its own pull-down on the wire to arbitrate at all. Reading the true resolved net is the accurate model, not a compromise — which is why nothing in `Circuit` changed.
  - **Disabled beats a faulted direction**: a chip that isn't driving can't put a fault on anything. Otherwise `Error` on either control dominates, and an undriven control gives `Unknown` rather than `HighZ` — claiming "deliberately out of the way" would be more than is known. Same reasoning as `TriStateBuffer`.
  - `tests/multi_driver.rs` covers both directions, the far bus floating when disabled, and the transceiver driving against a live source resolving to `Error` by the ordinary net rule.
  - **Pin labels are now a rule, not a series of exceptions**: a symbol carries text exactly when its pins are *not* interchangeable and its shape doesn't say which is which. Gates carry none — their inputs commute and the shape says in/out. `SrLatch` labels `S`/`R`/`Q`/`Q̄`; the transceiver labels `DIR` and its enable, leaving the two bus sides to the double-headed arrow. Everything else stays text-free.
- [x] **Both enable polarities of the transceiver**, rather than a choice between them (`BusTransceiver::active_low`/`active_high`, kinds `BusTransceiverOe`/`BusTransceiver`). I first shipped active-high labelled `OE` and flagged it as a wart; Romain asked to keep `OE` and invert it, then to have both. He's right that there's nothing to choose: `OE` active-low is the 74x245's polarity, `EN` active-high matches the tri-state buffer and every HDL primitive, and both appear in any real schematic. My earlier "internal consistency" argument for picking one was weak — each follows *its own* symbol's convention, which isn't inconsistency.
  - **The bubble is what makes this correct rather than merely different.** `OE` draws an inversion bubble on its pin and `EN` doesn't; that mark is the entire visible difference, since the variants are otherwise identical and the tri-state buffer's own enable is unbubbled *and* active-high. Renaming without the bubble would only have moved the lie.
  - Polarity is normalised to active-high at the edge (`BusTransceiver::asserted`), so there's one truth table rather than one per variant. Only the two definite levels flip — `Unknown`/`HighZ`/`Error` say nothing about polarity, and inverting them would invent information.
  - The electrical reason for active-low enables (a floating TTL input reads high, so the safe state is "off") **doesn't carry over**: an unconnected pin here reads `Unknown`. The convention is kept for recognisability, not for its original cause.
- [x] **A variant selector in the properties panel**, for the transistor's channel and the transceiver's enable polarity alike (`properties::VARIANTS`, `SimLogixApp::change_kind`).
  - **Romain asked for this as a *property*; it isn't stored as one, and shouldn't be.** The variant already lives in the `ComponentKind`, and the symbol is already drawn from the kind — so "the symbol follows" was free. Moving it into `Properties` would have cost a format migration and put the same fact in two places. An NMOS and a PMOS *are* two components, and a saved `simlogix:PTransistor` says more than a `Transistor` with a flag beside it. What was missing was the **gesture**, not the storage.
  - **Changing kind goes through the document, not through `Circuit`.** A component's identity in the engine is its `ComponentId`, which every wire endpoint refers to; swapping the boxed component in place would mean remapping all of them. Rewriting the kind in the saved form and reopening keeps routes, waypoints and colours exactly as they are, because wires are stored by *index*. It costs a rebuild — the one undo and circuit-switching already pay. The selection is recovered by position, since the rebuild hands out fresh ids.
  - Both palette entries stay: placing a PMOS directly beats placing an NMOS and converting it. The selector is for changing your mind.
- [x] **The `Button` symbol shows its cap down while held** — filled *and* sunk 2.5 px towards its pin. Two cues because neither carries alone: the travel is invisible at a glance, and a filled circle on its own reads as a lit LED. The fill takes the symbol's colour rather than a signal colour, because the cap being down is a *position*, not a level — the LED downstream is what reports the level.
  - `symbol::draw` grew a `SymbolState` for it. `label` was already an escape hatch used by `Probe` alone and `pressed` would have been the second, so they're now one struct: the next such need costs a field instead of a signature change at twelve call sites.
- [x] **Multi-selection, group move, and copy/paste** — the last of the v1 editing scope.
  - **`Selection { components, wires }` replaces the two mutually exclusive `Option`s.** `Delete` used to check the wire first so a stale wire selection couldn't shadow a component; a rubber band picks up whatever it lands on, so "which of the two is selected" stopped being a question worth asking. The properties panel edits a *lone* selection (`lone_component`/`lone_wire`) — several selected means no one set of properties to show.
  - **Rotation turns each component on its own centre**, not the group's: pins must land on the grid, and turning the group as a body would put them between dots.
  - **A wire is copied only when both ends are inside the selection.** One whose far end is a pin you didn't take has nowhere to attach, and inventing a loose end for it would paste something never selected.
  - **The clipboard is the *system* one**, carrying the fragment as JSON, and not for elegance: **egui only reports a paste when the system clipboard actually holds text**, so an in-app clipboard meant `Ctrl+V` silently did nothing whenever the real one was empty — which is most of the time. Pasting between two windows falls out as a consequence. A `simlogix_fragment` marker means pasting a URL or prose does nothing rather than being half-read. The Edit menu keeps an in-app copy as well, because a menu item has no way to read the system clipboard — egui only ever surfaces it through the `Ctrl+V` event.
  - **`Ctrl+C`/`Ctrl+V` are read as `Event::Copy`/`Event::Paste`, not as shortcuts.** egui converts those chords and `return`s, so the key press never arrives and `consume_shortcut` can never match. The menu shows the chords as labels only.
- [x] **A hand tool and a marquee tool** (`Tool::Pan`, `Tool::Marquee`), plus **Settings → Left drag**.
  - Romain asked for a "selection tool"; `Tool::Select` already existed, so the thing that needed naming was the *hand* — the arrow/hand pair. Then, since he pans more than he selects, the preference: left drag sweeps a selection (default) or moves the view. Both tools exist so whichever the preference takes away is still one click away, and the middle button always pans whatever the tool. That's why there is no "which gesture" setting to get wrong — the toolbar is the escape hatch.
  - `pans_on_left_drag()` and `bands_on_left_drag()` are deliberately *not* one negated: most tools do neither, and a left drag while wiring is neither a band nor a pan.
  - **Two regressions I caused and their shared cause**: the band was first a full-canvas `ui.interact`, which covered the `Scene`'s own background response — and placement *and* panning both go through that, so both silently broke while wiring kept working (it has its own targets, drawn on top). The fix was to add no widget at all: with `PRIMARY` removed from `drag_pan_buttons`, the scene's background drag was already free to read. A drag the background sees *is* a drag on empty canvas, since everything else claims it first.
  - **The group came apart by exactly one frame's delta**: `interact_box` deliberately doesn't move on the frame a drag starts (so the undo snapshot is the true pre-drag state), but `dragged_by` was computed from `response.dragged()`, which is already true then. The grabbed component stayed put while the rest of the selection advanced. Now one `applied_drag()` helper, named for what it returns — what was *applied*, not what the pointer did.
- [x] **Preferences persist** (`eframe`'s `persistence` feature, `Settings` + `SimLogixApp::new`). Chosen over a hand-rolled file because eframe already knows where preferences live on each platform — and egui's own state (theme, panel sizes, window geometry) comes along for free. Only what the user *chose* is stored: `language: Option<Language>` keeps `None` meaning "still following the OS locale", so changing a machine's locale still has an effect. Every field defaults, so a settings file from an older build still loads — the same rule the project format follows. **A trap closed on the way**: `reopen()` does `*self = Self::from_project(...)`, so opening a project or switching circuits was resetting the preferences; they're now preserved explicitly alongside the language.
  - **Reset to defaults** covers only what the Settings menu itself offers. Resetting the language clears the *choice* rather than forcing English — going back to following the locale is what the reset means.
- [x] **A shortcuts window** (`help.rs`, `? → Shortcuts and gestures`). Mouse **gestures** sit in the same tables as the key chords, because in this editor they're the less discoverable half — cutting a wire by right-clicking a segment, joining two loose ends by dropping one on the other, finishing a wire with Enter. A window called "keyboard shortcuts" would have left out the part that needed saying. The tables live in `i18n.rs` with the rest of the text: a second home for translated strings is how translations drift.
  - A test holds the three languages to the same *shape* (same sections, same row counts). It first asserted the same *text* in the key column too and failed on `Suppr` vs `Delete` — which was the test being wrong: a French keyboard has `Suppr`, `Entrée` and `Échap` printed on it, and listing names that aren't on the keys in front of you is worse than not listing them.
- [x] **Signal state can be hidden** (`C`, Simulation menu). Romain suggested Settings and asked where it belonged; **the request for a shortcut is what answers it** — Settings holds what you set once (theme, language, left drag), and something you flip while working belongs with what it affects. So it sits beside Run/Pause, and like pause it is **not persisted**: a way of working at a moment, not a preference.
  - **It hides the state, not the user's wire colours** — and with the state off a coloured net is drawn *in* its colour rather than ringed by it. The casing only exists to leave the core for the level; with no level to show, a casing around a core that reports nothing is just a thicker wire, so the colour takes the core. Components are untouched either way — a LED still lights, a probe still reads out. Only the wires go plain.
  - The status bar says so while it's off, or grey wires read as something broken rather than something chosen.
  - `egui::Checkbox` has no shortcut column, so the key goes in the label; the tick is worth more here than the alignment.
