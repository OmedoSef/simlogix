# SimLogix

> This file is the project's reference guide. It must be **updated on every new decision** (architecture, scope, convention) to stay the source of truth — including when switching machines.

Project name: **SimLogix** (Sim + Logic).

## Project context

Romain wants to replace Logisim with a tool that fixes his main frustrations:

- **Tedious canvas interaction**: placing/wiring gates and wires is slow and clunky.
- **Painful component appearance editing**: Logisim's shape editor is limited.
- **Poorly handled feedback loops**: circuits with combinational feedback (e.g. an SR latch in NAND) cause bugs/hangs in the simulation engine.
- **Dated UI/UX** (Swing/Java).

Goal: a cross-platform logic simulator, written in Rust.

## Architecture decisions

_(these are the decisions and their rationale; see Progress for what is actually built)_

- **2-crate Cargo workspace**:
  - `simlogix-core/` — circuit model + simulation engine, no GUI dependency, testable in isolation.
  - `simlogix-gui/` — schematic editor + rendering + real-time simulation loop.
- **GUI: egui / eframe.** Chosen over iced or Slint for direct control of the `Painter` (smooth custom rendering of gates/wires/grid) and the immediate mode which naturally fits a real-time simulation. Native cross-platform + WASM export possible later.
- **Simulation engine: discrete events with propagation delay.** This is the answer to the feedback-loop problem. Every component has a propagation delay (defaults to 1 logical tick); an input change schedules an output event at `t + delay` instead of propagating instantly. An event queue ordered by logical time processes events in order — like HDL simulators (Verilog). This avoids infinite recursion on a combinational loop by construction (an SR-NAND latch or ring oscillator converges/oscillates instead of crashing).
  - Oscillation detection: if a net changes state more than N times within the same time step, the engine stops and reports "unstable circuit" instead of freezing the UI.
- **Data model**:
  - `Signal::{High, Low, Unknown, Error, HighZ}` — the unknown/error state is planned from the start (one of the "simulation bug" irritants often comes from mishandling X/Z). `HighZ` is distinct from `Unknown`: `Unknown` means "not driven / not simulated yet", `HighZ` means "this specific driver is deliberately not driving right now" (tri-state).
  - `Pin`: input, output, or bidirectional (`PinDirection::InOut`) terminal of a component, connected to a `Net`.
  - `Component`: a trait with `eval(&self, inputs) -> outputs` + `propagation_delay()`. Sub-circuits also implement this trait (hierarchy is a first-class citizen, not a hack).
  - `Circuit`: graph of components + nets, event queue, logical clock.
  - **Multi-driver nets** (implemented — `Circuit::resolve`): a net can have more than one potential driver, which is what a bidirectional/tri-state buffer needs. Resolution rule when computing a net's `Signal`: ignore drivers reporting `HighZ`; if 0 remaining drivers → `Unknown`; if 1 → that driver's value; if ≥2 with differing values → `Error`. `Transistor` already relies on this by driving `HighZ` when it isn't conducting; no component exposes a true bidirectional pass yet.
- **Dev container** (`.devcontainer/`): `rust:1-slim-bookworm` image + X11/GL/GTK libs needed by eframe (`libx11-dev`, `libxkbcommon-dev`, `libgl1-mesa-dev`, `libgtk-3-dev`, etc.), `clippy`/`rustfmt` installed. The host's X11 socket (`/tmp/.X11-unix`) is mounted and `DISPLAY` propagated, so `cargo run` from the container opens the window directly on the host desktop (X11 forwarding). The host's D-Bus session socket (`${localEnv:XDG_RUNTIME_DIR}/bus`) is mounted the same way, with `DBUS_SESSION_BUS_ADDRESS` propagated — this lets `rfd`'s native file dialog (used for save/load) reach the host's real `xdg-desktop-portal` instead of needing a portal running inside the container (there isn't one). Tried forcing `rfd` onto its `gtk3` feature first as a workaround; reverted once the D-Bus forward worked, since `gtk3`'s gtk-rs bindings are unmaintained (`cargo audit` flagged them) and the portal is the more correct approach anyway. `remoteUser: vscode` to stay consistent with the pattern already used on `file-checker`. The container is only for the build/dev toolchain (source code is bind-mounted by VS Code, not copied into the image).
  - `cargo install cargo-audit`/`rustup component add` in the Dockerfile must run **after** switching to `USER vscode`, not before — running them as root first leaves root-owned files in the shared cargo registry cache that later block `vscode` from writing new entries (`Permission denied`). Learned this the hard way after a devcontainer rebuild.
  - `cargo build --release` inside the devcontainer produces a binary at `target/release/simlogix-gui` that also runs directly on the host (bind-mounted, so no copy needed) — the container's Debian bookworm has an older glibc (2.36) than a typical host, and glibc is forward-compatible, so this direction works. Confirmed working on the host's real Ubuntu 24.04 desktop, including the native save/load dialog (no forwarding needed there, since it's not sandboxed in a container).
  - Practical setup instructions (`xhost` prerequisite, how to open the devcontainer): see [README.md](README.md), not duplicated here.

## v1 scope / Out-of-scope

**In v1 (minimal simulator):**
- Basic gates: AND, OR, NOT, NAND, NOR, XOR, XNOR, buffer.
- Bidirectional/tri-state buffer (bus transceiver) — added to scope because Romain will need it; requires the multi-driver net resolution described above.
- Input (switch/button), output (LED), clock.
- Schematic editing: placement, wire routing with grid snapping and orthogonal routing, rotation, multi-select/move.
- Real-time simulation wired into the UI loop.
- Save/load a circuit (serde).

**Out of scope for v1** — kept as the reasoning of the time; the live list of
what's next is [ROADMAP.md](ROADMAP.md), and it is the one to update:
- A full custom appearance *editor* (user-drawn symbols) — v1 ships hand-coded vector symbols per component kind instead (see the "Component appearance" convention below), not a UI for drawing your own. This is Romain's pain point #2; a real editor is addressed after the core is solid.
- Multi-bit buses, memory (RAM/ROM), VHDL/FPGA export, collaboration.

## Working conventions

- **We move forward together, step by step.** Don't scaffold or write large chunks of code at once without validation — propose a step, discuss, then implement.
- This file must be updated as soon as a new structuring decision is made (architecture, scope, convention) — not only at the end of a session.
- Always check that this file reflects the actual state of the code before fully relying on it (the code is authoritative in case of divergence).
- **Dev tooling**: `rust-toolchain.toml` (pins Rust 1.97.1 + clippy/rustfmt), `.editorconfig`, `pre-commit` hook (`fmt --check` blocking + `clippy` informational, consistent with the choice not to `deny(warnings)` yet), `cargo-audit` installed in the image (RustSec scan, run manually for now). Details: [documentation/contributing/dev-tooling.md](documentation/contributing/dev-tooling.md).
  - **CI exists now** (`.github/workflows/`), because the recorded trigger — deciding to ship a version to the world — arrived. Details: [documentation/contributing/releasing.md](documentation/contributing/releasing.md). Two deliberate differences from the local hooks: **clippy is blocking here** (a hook must not stop a commit mid-thought; a pull request is exactly where an unaddressed lint should be caught — and the pinned toolchain is what makes `-D warnings` safe), and **`cargo audit` is not part of CI** but runs weekly, since the advisory database changes daily while the code does not, and a red mark meaning "not your fault" is one people learn to ignore.
  - **Releases are cut by pushing a `v*` tag**; nothing in `.github/` is edited to do it. Artefacts: portable archives for Linux, Windows and both macOS architectures, a `.deb`, and an `.msi`. Every archive carries `LICENSE` and `THIRD-PARTY.md` — the notices are compiled in too, but an archive is a copy being distributed and attribution has to travel with a copy.
  - **`$auto` was not enough for the Debian dependencies**, and that mattered: X11, Wayland, EGL and xkbcommon are all `dlopen`ed, so they leave no `NEEDED` entry to read off the binary. The generated package depended on libc alone — it installs cleanly and then won't start, which is worse than refusing to install. The list is taken from the `.so` names in the binary itself.
  - **Both packagers ship the dev tools unless told otherwise.** `cargo-deb` with no asset list installs every binary the crate builds, and `cargo wix init`'s template does the same — so `write-icon` and `write-licenses` were on their way onto users' machines. Both are now explicit lists of one binary. The `wix/main.wxs` is checked in and edited away from that template (a Start Menu shortcut, an icon, no `PATH` entry); re-running `cargo wix init` would overwrite it.
  - **`assets/icon.ico` comes from the same `write-icon` tool as the PNG**: an icon file is a twenty-two byte header around a PNG, so there is no second rasteriser and no second encoder. The Windows *executable* still has no embedded icon — that needs a build script and a build-dependency, and is deferred.
  - **`scripts/release.sh` is the way a release is cut**, rather than a sequence to remember. The version lives once (`[workspace.package]`), both crates inherit it, and it reaches the About window through `CARGO_PKG_VERSION` — so one edit changes the number a user sees. The script refuses rather than surprises: not off `main`, not with a dirty tree, not onto a tag that already exists locally *or on the remote*, and not without the checks CI will run. It also regenerates the third-party notices into a temporary directory and compares — shipping stale attribution is shipping the *wrong* attribution. A failed check restores the tree via an `EXIT` trap, so a failed run leaves nothing behind.
  - **What was actually verified**: the Debian package was built, installed, listed and removed in the container, and its desktop entry validated; every workflow parses. The Windows and macOS paths were written on a Linux machine and have never been run — the first evidence will be the first workflow run.
  - **Windows and macOS are switched off from v0.7.0 on**, and *commented out* rather than deleted. Romain has neither machine, so nothing those jobs produced could be tried before it reached someone — building is not running, and an artefact nobody has run is a promise made on the strength of having compiled. Every release spent runner minutes keeping that promise standing.
    - The three matrix entries and the whole `windows-installer` job are still there, and so is everything they need: `wix/main.wxs`, the archive step's Windows branch, both Apple targets. Bringing them back is uncommenting them **and** putting `windows-installer` back in `publish`'s `needs` — which had to come out, or every release would wait forever on a job that never runs.
    - **CI went Linux-only as well**, in the same commit but as a separate decision, and it was worth asking separately: building on three platforms checks that the code still *compiles* everywhere, which is not the same as promising an artefact. What settled it is that nothing is shipped for those platforms any more, so the check guards a promise no longer made — and it is three runners on every push, where a release is rare. **The cost, named rather than glossed**: code that stops compiling off Linux now surfaces the day those releases come back, not on the push that caused it.
    - The `README` and `releasing.md` were changed with it. A release that ships Linux alone while the documentation promises four platforms is worse than one that ships nothing: the docs are the only thing a visitor has to go on.
  - **The old entry, kept for the reasoning that led here**: No CI, deliberately, until there's a first public release. (superseded)  Romain's call: while he's the only one pushing and the local hooks run `fmt`/`clippy` on every commit, a pipeline would guard against a contributor who doesn't exist yet. The trigger to add it is deciding to ship a version to the world — not project size, and not a run of green builds. Don't re-raise it before then.
  - `cargo audit` had flagged 2 transitive vulnerabilities (`quick-xml` 0.30) and 2 unmaintained crates (`paste`, `ttf-parser`) via the eframe/accesskit dependency chain. Fixed by upgrading `eframe`/`egui` 0.29 → 0.35 (this required adapting `simlogix-gui`: `eframe::App::update(&Context, ...)` became `ui(&mut Ui, ...)` in 0.35). Only remaining flag is `ttf-parser` unmaintained (warning, not a vulnerability) — `cargo audit` now exits clean.
- **Licence: MIT**, with the notices of everything it depends on carried alongside. Details: [documentation/licensing.md](documentation/licensing.md).
  - Romain asked for terms permitting reuse **with attribution**, which is MIT exactly. Chosen over the Rust ecosystem's usual MIT-or-Apache-2.0 pair because that pair's only addition is an explicit patent grant, which matters when contributors hold patents reading on the code — not the situation here. Adding it later is always open, since a copyright holder may offer further terms at any time; taking a licence away is not.
  - `[workspace.package]` holds the licence, repository and version once, so the two crates cannot come to claim different ones.
  - **`THIRD-PARTY.md` is generated** (`write-licenses`, the second tool after `write-icon`) from `cargo metadata` plus the licence files in the cargo registry. 421 dependencies, 708 KiB — about 50 KiB once git packs it. Only the **normal** graph: dev- and build-dependencies build the tests and run at build time, and neither reaches a released binary.
  - **Two outputs, one pass.** The first version showed `THIRD-PARTY.md` in the window as plain text, which put `| crate | 1.2 | MIT |` and `[name](url)` on screen literally — Romain's verdict was that it looked filthy, and he was right: that is a marked-up file being displayed rather than a list being presented. The tool now writes the Markdown *and* a JSON form from the same in-memory value by the same call, so they cannot drift; the window reads the JSON and draws a searchable table, with the 190 licence texts behind collapsing headers. A closed header draws none of its body, which is what keeps 700 KiB off every frame without any laziness of our own.
  - **The notice is embedded as well as checked in**, via `include_str!`. The obligation is attribution, and attribution has to reach whoever ends up with a copy — a file beside a binary can be separated from it, text compiled into one cannot. Rendered by `ScrollArea::show_rows`, since handing 700 KiB to egui as a single label would lay out every line on every frame.
  - **Texts are deduplicated by content**: 2.4 MB of licence files become 708 KiB. Apache-2.0 is byte-identical wherever it appears; MIT differs by its copyright line and so genuinely repeats — that line *is* the attribution, and collapsing it would defeat the point.
  - A dependency declaring no licence is written as `NOT DECLARED` rather than guessed at, and **a test fails on it**. Today none do, and nothing in the tree is copyleft — everything is MIT, Apache-2.0, BSD, ISC, Zlib, Unicode-3.0 or a public-domain dedication.
- **[ROADMAP.md](ROADMAP.md) holds what isn't built yet**, in roughly the order it's worth building, with the reason for each. Kept apart from this file on purpose: `CLAUDE.md` is the record of decisions *taken* and grows by appending, so a list of intentions buried in it would go stale unnoticed. When something ships it leaves the roadmap and its reasoning is written here — the two never describe the same thing.
- **Conventional Commits** (`feat:`, `fix:`, `docs:`, etc., scope = name of the crate/area touched). Enforced locally by a `commit-msg` hook versioned in `.githooks/`, wired up automatically in the devcontainer via `postCreateCommand`. Details: [documentation/contributing/commit-conventions.md](documentation/contributing/commit-conventions.md).
- **User/contributor documentation**: [documentation/](documentation/README.md) folder, in English, split into subfolders (`getting-started/`, `architecture/`, `contributing/`) to avoid overloading the README. Grows along with features. CLAUDE.md remains the internal decision log ("why" + progress); documentation/ is the "what/how" for an external reader.

## Code conventions

- **Language**: identifiers (types/functions/variables) in English (standard Rust convention); comments and doc-comments (`///`, `//!`) also in English. **Everything written is in English**, `README.md` included — it was in French until the question of a public release came up, and the README is the first thing a visitor reads. `CLAUDE.md` is in English too (switched from French on request, for consistency rather than any functional reason). Romain and I converse in French; that is the one thing that stays.
- **Error handling**: custom errors via an `enum` + [`thiserror`](https://docs.rs/thiserror) (no raw `String` errors, no `anyhow` in `simlogix-core` — it's a lib, callers need to be able to match on precise variants).
- **Panics**: `panic!`/`unwrap()`/`expect()` forbidden outside `#[cfg(test)]`. An invalid input or malformed circuit must always surface as a `Result`, never panic.
- **Formatting/linting**: `cargo fmt` (default config, no `rustfmt.toml`) and `cargo clippy` before considering a step done. No custom clippy config for now (may tighten later — `deny(warnings)`, `pedantic` — if needed).
- **Tests**: unit tests co-located in a `#[cfg(test)] mod tests` module at the bottom of the file they test, preceded by a banner comment separating it from the real code:
  ```rust
  // -----------------------------------------------------------------------------
  // Tests
  // -----------------------------------------------------------------------------

  #[cfg(test)]
  mod tests {
  ```
- **Module organization**: one file per concept — `signal.rs`, `pin.rs` (`Pin`, `PinDirection`), `net.rs` (`NetId`, later `Net`), `component.rs` (the `Component` trait only), `circuit.rs`. `lib.rs` stays just crate doc + `mod`/`pub use` declarations, nothing else. Once there are several concrete components (gates, `Button`, `Led`...), they go under a `components/` subfolder rather than piling into `component.rs`. Each file keeps its own `#[cfg(test)] mod tests` at the bottom.
  - Same principle applies to `simlogix-gui`: `main.rs` stays just `mod` declarations + `fn main()`. `app.rs` (`SimLogixApp`, the `eframe::App` loop), `canvas.rs` (grid + generic box/pins rendering, `BOX_SIZE`/`snap_to_grid`), `palette.rs` (`ComponentKind`, the palette panel), `placed_component.rs` (`PlacedComponent`: draw + interact for one placed instance).

- [x] **Feedback-loop tests** (`simlogix-core/tests/feedback.rs`) — the founding architectural claim, finally under test rather than only in prose.
  - **Integration tests, not unit ones**: they drive `Circuit` plus several concrete components through the public API alone, so there's no single file to co-locate them in. First use of `tests/` in this project; the co-location convention still stands for unit tests.
  - **The SR-NAND latch test turns on the *hold* case**: same inputs, opposite output depending on history. That's memory out of a purely combinational loop, which is exactly what an instantly-propagating engine can't produce — set, hold, reset, hold.
  - **A ring of plain inverters would have tested nothing.** `Not(Unknown)` is `Unknown`, so an undriven ring stays undriven forever and the test would have passed without ever oscillating; real silicon starts on noise, this needs a definite value put in deliberately. The ring is therefore `Nor` + 2 × `Not`, the `Nor` doubling as an enable that seeds it.
  - **A prediction of mine was wrong, and the engine is better than I claimed.** I expected the forbidden-state release (both active-low inputs asserted, then both released together) to oscillate and be reported as unstable. It settles: the tie is broken by the order the two gates happen to be evaluated in, landing on a legal complementary state — what Verilog-style simulators do. The test asserts it leaves the forbidden state, deliberately *not* which way it falls, since that's an implementation detail rather than a promise.
  - **`run()`'s known trade-off is now pinned by a test** rather than living only in prose: draining a healthy oscillator trips `MAX_TOGGLES_PER_NET`, because the toggle counter is per `advance()` call. The GUI uses `advance` in small steps for that reason.

- [x] `Clock` component (`components/clock.rs`) — a periodic source, alternating `Low`/`High` every evaluation. Required real engine changes, not just a new `Component` impl:
  - **`Circuit::schedule_periodic(component, period)`**: marks a component as self-rescheduling forever after every evaluation (`evaluate()` reschedules it at `clock + period` unconditionally, on top of the normal reader-rescheduling logic). Without this, a `Clock` would tick exactly once and go silent — it has no inputs, so nothing would naturally re-trigger it.
  - **`Circuit::advance(ticks)`**: processes events up through `clock + ticks`, then *stops* — unlike the old `run()` (drain until empty), which would never return once a periodic component exists, since the queue is never truly empty. `run()` still exists, now defined as `advance(MAX_RUN_TICKS)` (a large but finite bound: 1,000,000) purely so it can never hang — existing tests/call sites didn't need to change, but **`run()` is the wrong tool for a clocked circuit**: it can legitimately trip `MAX_TOGGLES_PER_NET` (a fast clock ticking that many times looks indistinguishable from genuine instability) and, worse from the GUI's side, it would let any placed clock burn through a huge chunk of its future ticks in one synchronous burst.
  - **GUI**: `SimLogixApp::ui()` now advances the circuit by real elapsed time *every frame* (`TICKS_PER_SECOND = 60`, accumulated via a fractional `tick_budget`) and calls `ctx().request_repaint()` unconditionally — this is what makes a placed `Clock` visibly tick at a real, wall-clock-tied rate (`CLOCK_PERIOD_TICKS = 60` → 1 toggle/second) instead of free-running as fast as the CPU allows. Tradeoff: the app now redraws continuously (higher idle CPU use) regardless of whether a `Clock` is present, not just on input, to keep this working. All the interactive-settle call sites (button press, wire connect/disconnect, project load) were switched from `run()` to `advance(SETTLE_TICKS)` (a small constant, 32) for the same reason — calling `run()` from *any* interaction would also burst-advance any clock elsewhere in the circuit.
- [x] Fixed a real pin-alignment bug found while testing the clock: multi-pin edges (e.g. a `Transistor`'s `G`/`S`) were positioned by fractional interpolation across the box's height, which doesn't land on the grid except by coincidence for exactly 1 pin. `canvas`'s pin-spacing helper now places each pin a whole multiple of `GRID_SPACING` from the box's center instead.
- [x] Settings menu: light/dark theme (defaults to OS theme via egui's `ThemePreference`/`Theme`), and a language picker (English/French/Italian, defaults to OS locale) — see the i18n convention below.
- [x] Palette reorganized by category (Sources/Outputs/Transistors), each entry showing an icon + name; the canvas now shows only the icon (see "Component appearance" convention below) — the previous auto-generated "box + named-pin-text" appearance is gone.
- [x] **Component appearance convention (standing decision)**: every component kind gets a hand-drawn vector symbol in `simlogix-gui/src/symbol.rs`, not a generic box. No enclosing box, no text labels (not even pin names) — a pin's exact position is wherever that symbol's own lead line ends, not an independently-computed generic offset; the symbol owns its `PinPositions`, returned from `symbol::draw`. A symbol is defined once in its canonical `Rotation::Deg0` layout; `symbol::rotate` rotates every point of it (geometry and pins together) for the other 3 rotations, so the icon and its pins always agree at every rotation instead of only the pins moving. `BOX_SIZE` (`canvas.rs`) is deliberately sized so its half-extents are whole multiples of `GRID_SPACING` — since a symbol's pins sit at the box's own edges/corners, this is what keeps every pin landing exactly on a grid dot. **Going forward, every new component gets a real symbol here by default** — falling back to placeholder/no-symbol rendering only if Romain explicitly asks for it, or if a sensible symbol genuinely doesn't exist yet for that kind.
- [x] **All 8 v1 logic gates**: `And`/`Or`/`Nand`/`Nor`/`Xor`/`Xnor`/`Not`/`Buffer` (`simlogix-core/src/components/`), each combinational (no internal state). 2-input gates resolve uncertain inputs by dominance (e.g. `And`: a definite `Low` on either input forces `Low` regardless of the other; short of that, `Error` dominates; short of that, anything but both definite is `Unknown`) — mirrored for `Or`/`Nand`/`Nor`. `Xor`/`Xnor` have no dominant input (either input alone still leaves the output dependent on the other), so both inputs must be definite to resolve; `Error` still dominates over plain uncertainty. `Not` inverts (`HighZ` and `Unknown` both resolve to `Unknown`); `Buffer` passes every signal state through unchanged. New "Gates" palette category. GUI-side, this is fully generic — adding a gate of the same shape needs no new `PlacedComponent` variant:
  - **2-input gates** (`PlacedComponent::TwoInputGate`, `placed_component.rs`): two inputs at pin index 0/1, one output at pin index 2 — same shape for `And`/`Or`/`Nand`/`Nor`/`Xor`/`Xnor`, added via `PlacedComponent::two_input_gate(id, center, kind)`.
  - **1-input gates** (`PlacedComponent::OneInputGate`): one input at pin index 0, one output at pin index 1 — `Not`/`Buffer`, via `PlacedComponent::one_input_gate(id, center, kind)`.
  - Symbols (`symbol.rs`) share drawing code within each shape family via an `invert: bool` (and `xor: bool` for the OR family) parameter, plus a shared `bubble_end` helper that draws the small inversion "bubble" and returns where the lead past it continues — `draw_and_gate(..., invert)` covers And/Nand, `draw_or_gate(..., xor, invert)` covers Or/Nor/Xor/Xnor, `draw_triangle_gate(..., invert)` covers Buffer/Not. Mirrors the existing `draw_transistor(..., is_n_type)` pattern.
  - Adding a genuinely new shape (a gate that doesn't fit either family) still follows the checklist: `ComponentKind` variant in `palette.rs` (+ its `category_gates` entry), a `component_xxx` label in `i18n.rs` (3 translations), a `draw_xxx` in `symbol.rs`, and a `place()` arm in `app.rs`.
- [x] **Multi-waypoint wire routing with explicit `Wire` objects**, replacing both the old drag-from-pin-release-on-pin gesture (single automatic bend) and, shortly after, the "infer topology from net membership" render model entirely. Wiring is click by click: click a pin to start a wire, click anywhere on the canvas to drop as many grid-snapped waypoints as wanted, click a pin — or an existing wire's waypoint, tapping into it as a junction — to finish (Escape cancels).
  - **`SimLogixApp.wires: Vec<Wire>`** is now the source of truth for both rendering and editing (`next_wire_id: u64` hands out stable ids, `selected_wire: Option<u64>` selects by id — no more `(NetId, usize)` keying, and with it the **known instability** that came from indexing into an arbitrary net-membership grouping is gone). A `Wire` has `net`, `from: (ComponentId, usize)` (every wire starts from a real pin), `to: WireEndpoint` (`Pin(ComponentId, usize)` or `Junction(Pos2)` — a fixed point tapping into another wire), and `waypoints: Vec<Pos2>`. `SimLogixApp.wiring_from: Option<WireInProgress>` (`from`, `net`, `anchor`, accumulated `waypoints`) tracks a wire mid-creation.
  - **Why the rewrite, not a patch**: the old model rendered each net as a "star" from an arbitrary anchor pin to every other pin sharing it, inferred fresh each frame from `Circuit` net membership. That has no way to represent a wire ending on a point that isn't a pin at all — which is exactly what a junction is — so bolting junctions onto it would merge the net correctly but render the new wire wrong (a fresh auto-routed line from an unrelated anchor, ignoring the path actually drawn to the junction).
  - **Junction endpoints track their host live** (fixed shortly after shipping the static version above, once Romain hit it in practice): `WireEndpoint::Junction { wire: u64, waypoint: usize }` references the host wire's id and which of its waypoints, not a frozen `Pos2` — so dragging that point (even the host's own implicit default-route point, which materializes into a real waypoint the moment it's first dragged) drags every tap on it along too. Resolved fresh every frame in a pre-pass (`ui()`, a `HashMap<u64, Resolved>` built by iterating `self.wires` in creation order) rather than recursively, since a wire can only tap into an *already-existing* — so already-resolved — earlier wire; that ordering guarantee is what makes a single forward sweep enough, no cycle handling needed. Deleting a wire cascades to anything junction-tapped onto it (and transitively onto *those*), so a delete never leaves an orphaned tap silently un-renderable and un-selectable; same cascade on deleting a component, since removing its wires has the same orphaning risk.
  - **Deletion**: disconnects whichever endpoint is a real pin uniquely belonging to that wire (`to` if it's a `Pin`, else `from`, since a `Junction` has no pin of its own) via `Circuit::disconnect_pin` — same "give this one pin a fresh net, everyone else stays connected" semantics as before, which turns out to generalize correctly to junctions without special-casing: deleting a tap wire only detaches its own pin; deleting a host wire only detaches its own far pin, leaving anything junction-tapped onto it (still on the same underlying net) unaffected. **Superseded** by the derived net model below: deleting a wire is now just removing it from the drawing, and no pin is detached by hand at all.
  - **Post-hoc reshaping**: every waypoint has its own visible dot and drag handle, snapped to grid on release; double-clicking a wire inserts one, right-clicking one removes it. (The automatic mid-wire Z-bend this originally materialised from has since been removed — see below.)
  - **Save/load** originally kept deriving wire *groups* from net membership, so shape and junctions weren't persisted. Superseded: the format now stores wires explicitly (see the project-format entry below).
  - **Deselection**: clicking empty canvas clears the selection (tracked by a per-frame `click_consumed` flag — set by anything selectable that claims the click: a component, a wire, a waypoint, a pin — so "hit nothing" is a real signal rather than a guess), and Escape/right-click backs out one step at a time: a wire in progress first, then, once there's none, the selection and any queued placement. Selecting a component and selecting a wire are also now mutually exclusive — `Delete` checks the wire first, so leaving a stale wire selected while clicking a component would have deleted the wire instead of the component just clicked.
  - **Fixed a real bug found immediately after shipping the click-based interaction**: a component's own drag/click area (its full box rect) overlapped every pin's hit-rect (pins sit exactly on the box's edge), and since the box's `ui.interact()` ran first, a click meant to start a wire on a pin could get claimed by the box instead and move the component. Fixed by insetting the box's interactive rect by `PIN_HIT_MARGIN` (`placed_component.rs`, half a pin's hit-rect size) so the two never overlap — drawing/symbol geometry is untouched, only the interactive area shrank.
  - **1-input gates** (`Not`/`Buffer`) needed their own `PlacedComponent::OneInputGate`, since they don't fit `TwoInputGate`'s shape. Both are done.

- [x] **Wires became first-class drawable objects**, in a sequence of steps that each removed a special case rather than adding one:
  - `WireEndpoint` is `Pin` | `Junction { wire, waypoint }` | `Free(Pos2)`, and **both** ends use it. Deleting a component therefore keeps its wires, cut loose where the pin was — the cost is asymmetric (deleting an unwanted wire is one click; redrawing a wanted one is not), and dragging a loose end onto the replacement is exactly how you swap a gate.
  - **Deleting no longer cascades.** It used to delete every wire tapped onto a deleted one, to stop an orphaned tap resolving to nothing and silently vanishing. That was deleting user data to hide a rendering bug; making the orphaned state representable (`Free`) was the actual fix.
  - **Junctions track their host live** (by wire id + waypoint index, resolved every frame) rather than freezing a position, so moving a contact point drags its taps along. Resolution iterates to a fixpoint instead of assuming creation order, which is what lets a wire be re-attached to *any* other one.
  - **Splitting and joining** are inverses: right-clicking a segment cuts it, and dropping two loose ends together rejoins them (`reverse_wire` first lines the two up, mirroring junction indices). A cut originally had to work out whether the pieces really ended up separate before detaching the far pin — a tap bridging the cut point keeps them joined. The derived net model below deleted that reasoning outright: cutting changes the drawing, the drawing is re-read, and a bridged cut simply comes back as the same group.
  - A wire is exactly the points it was given; the implicit mid-wire Z-bend is gone. For a level wire it produced *two* points at the same spot, which surfaced as a stray point on top of an end after a cut. Removing it also deleted the "phantom point that only becomes real once dragged" special case from three call sites.
  - `Wire` no longer caches its net: nets are reallocated wholesale on every edit, so a stored copy goes stale as soon as anything elsewhere in the drawing changes — visible as a wire drawn in the wrong signal colour. It's read back from whichever end reaches a pin, following junctions, with a cycle guard.

- [x] **Geometric net model**: connectivity is now *derived from the drawing* after every edit, instead of being accumulated as wires are drawn. This is the model KiCad and Logisim use, and it closes the known limitation logged above — two separate wires between the same pins, one of them cut, stay connected.
  - **Why the previous model couldn't be patched**: a destructive merge doesn't remember *why* two pins ended up together. Once `merge_nets(a, b)` has run, nothing records whether one wire or three put them there, so `disconnect_pin` on a delete could only guess. Every fix built on it was a special case compensating for that missing information (does a tap bridge the cut? did the pieces really separate?) — the information simply wasn't there to consult.
  - **`Circuit::rewire(&[Vec<(ComponentId, usize)>])`** replaces `merge_nets`/`disconnect_pin` (both removed — keeping a second, contradictory way to manage connectivity is exactly how the two would drift apart). The caller owns the drawing and hands over the groups of pins it says are connected; `rewire` throws away the whole pin→net mapping and allocates one fresh net per group, plus one per pin no group mentions. Contributions already driven onto a net **follow their pin**, so nothing has to be re-evaluated to get the values back, and only components whose *inputs actually changed* are rescheduled — which is what keeps a `Clock` (no inputs, hence never disturbed) from having its phase reset on every unrelated edit. Tested, including that clock case.
  - **`drivers` re-keyed** from `HashMap<NetId, HashMap<ComponentId, Signal>>` to `HashMap<NetId, HashMap<(ComponentId, usize), Signal>>`, i.e. per *pin* rather than per component. Needed so a contribution can follow its pin through a rewire — and it fixes a latent bug on the way: two output pins of the same component on one net used to overwrite each other's contribution.
  - **GUI side, `SimLogixApp::rebuild_nets`**: union-find over `Node::{Pin, Wire}`, each wire unioning itself with whatever its two ends touch (a `Free` end contributes nothing), then every group holding more than one pin goes to `rewire`. Driven by `connectivity_fingerprint()` — a hash of the component ids and each wire's id plus its endpoint *kinds*, deliberately blind to positions and waypoint indices, so dragging a wire around costs nothing and only a real topology change triggers a rebuild.
  - **Net churn is the accepted cost**: every edit allocates brand-new `NetId`s, so a `NetId` is only meaningful within one frame. Nothing stores one across edits (`Wire` reads its net back from its endpoints, `selected_wire` is a wire id), so this is already true in practice — but it's a real constraint on anything added later.

- [x] **Project format v4 — a zip container**, extension `.slgx` (the old `.simlogix` was too long to type). `project.json` lists the circuits in order, one file each under `circuits/`.
  - **Why**, in Romain's words: he moves between machines, and he wants *one file* to carry rather than a folder to keep together. That rules out the KiCad-style directory, which was the alternative I put up. The second reason is forward-looking: a container has somewhere to put things that aren't JSON, and the roadmap's custom appearance editor will want to store user-drawn symbols. Introducing it now costs an evening; introducing it once projects exist on disk costs a migration. It is *not* for speed — the whole document is read into memory either way, and always will be.

Mitigated by storing entries **uncompressed** (`CompressionMethod::Stored`) — these documents are kilobytes, so compression buys nothing, while a deflate stream is rewritten wholesale by a one-character edit, which is precisely what makes a compressed container hostile to version control. Uncompressed also keeps the contents greppable from outside the app.

So a renamed file still opens, and every v1–v3 file keeps working with no special handling — the existing migrations are untouched, and `from_json` is now documented as the pre-container reader.

Sanitising also means a name containing `/` or `..` can't reach outside `circuits/` — tested.
  - **Latent bug the version bump exposed**: `from_json` left `version` at whatever the *file* said for the no-migration branch, so a v3 file parsed to a struct claiming version 3. Harmless while `CURRENT_VERSION` was 3, wrong the moment it wasn't. The stamp now happens once at the end of `from_json` for every branch, rather than inside each migration where the branch needing no migration is exactly the one that forgets.

- [x] **Folders in the circuit tree (format v6)**, so circuits can be filed rather than living in one flat list.
  - **A folder is part of a circuit's address**: the reference is `library:folder/name`, so a name only has to be unique *within its folder* — `alu/adder` and `fpu/adder` can both exist. I argued the opposite first (folder as pure presentation, `library:name`, names unique project-wide) on the grounds that identity must not follow location. **Romain rejected the argument and was right**: renaming a circuit already breaks references, so "moving breaks references" is a difference of degree, not of kind. The one argument that survives — renaming a *folder* breaks references to every circuit inside it, including ones you never touched — wasn't enough against being able to name two circuits the same in different folders. Repairing references within a project is deferred to the sub-circuit work; references from another project will need pointing at the new address by hand.

  - **Renaming a folder changes only its own segment** (a `/` is refused): renaming must not double as moving. Everything filed under it re-paths with it, which is prefix work — and the test that matters is that `alu2` doesn't move when `alu` is renamed.

  - **The component holds no state and is told nothing.** The bus's width and each branch's width arrive in the *shape* of the signals it is handed, since a net is as wide as the drawing said — so there is no second copy of the widths here to drift from the drawing. A bit nobody drives from the far side is answered `HighZ` and not `Unknown`: it genuinely is not driving, and `Unknown` is a contribution that would fight everyone else.
  - **A width per pin was the prerequisite**, and finding that out is why it was done first — a splitter's bus and branches are of different widths by definition.
  - **Widening a splitter changes how many pins it has, which a built component cannot do.** So that edit goes through the document and reopens, exactly as changing a component's *type* does; `change_kind` was generalised into `edit_saved_component` rather than a second copy of it being written. And `place` gained `place_with(kind, center, &Properties)`: for a component whose shape *is* one of its properties, building it before knowing them cannot work — the first version rebuilt a 2-branch splitter with one branch and the test caught it.
  - **`set_component_properties` came out of `draw`** so the panel and a test do the same thing. The rebuild above is exactly the sort of wiring that stays green in a unit test while being wrong in the application — which is the pattern the interface tests exist for.
  - **The symbol carries text**, by the rule the SR latch and the transceiver already follow: branch pins are not interchangeable and nothing about their position says which carries bits 4 to 7. `bit_range` is shared with the properties panel, which names the same branches. The box grows a grid row per branch, computed by one `splitter_rect` read by both the drawing and the hit area — the lesson of the rotated component that could not be clicked.
  - Tested at both levels and each checked against its own sabotage: six unit tests on the component, four in a real `Circuit` — the echo is invisible to a unit test, since handing `eval` its inputs directly is precisely what removes it — and two through the document. Making the splitter hear itself again fails exactly the test that names it, holding `0b1001` after the port let go.
- [x] **A review after the splitter shipped, which found three faults rather than none.** Romain asked what was worth adding to the roadmap; two of the answers belonged in the code.
  - **`connectivity_fingerprint` was blind to a splitter's branch widths.** It hashed `properties().width()`, so regrouping `[1,3]` into `[2,2]` — same pin count, so no rebuild through the document — left two nets at their old widths. Fixed at the root rather than by adding the branch list beside it: it now hashes **each pin's width**, read exactly the way `rebuild_nets` reads it. The component's own `width` property was never the right question; it was merely the same answer while every pin was alike.
  - **The inspector reported a per-component width**, so a splitter's branch pins were all measured against the bus and its "width mismatch" marker would have fired on every one of them. In the one window whose whole job is to say where a real disagreement is. `Named` carries `pin_widths` now.
  - **Two interface tests built `Named` by hand**, which is how a test comes to check something the application never does — one of them asserted a label the app would never produce. `named_components` is a method now, and the test that wanted a user's name *sets the property* instead of fabricating the row.
  - **Two suspicions were wrong, and checking beat guessing.** An instance does follow its circuit being edited (switching circuits goes through `reopen`, which re-flattens) — kept as a test rather than a roadmap entry. And `all_ones`/`PortDrive::level` already guard their shifts at 64 bits, so the width ceiling cannot panic.
  - **Two roadmap entries had gone stale in the direction that misleads**: RAM/ROM and the mux/demux both said "wants buses first", and buses are here. A blocker that is no longer a blocker is worse than no note.
- [x] **Fixed: a probe on a bus was ringed as faulty while reading it correctly.** Romain's screenshot — a 4-bit port, a probe, both showing `C`, and the probe's pin in red.
  - **A pin now declares a width or declares *nothing*** (`pin_width` answers `Option<usize>`). `None` is not "one bit": such a pin never widens a net and can never disagree with one. The probe used to say 1, which is a claim, and the fault machinery was right to complain about it — the mistake was that it made a claim at all.
  - **The distinction is instrument against component**, and it is worth stating because the `Led` is deliberately the other way. A probe *measures* a net; being wrong about what it measures is not a thing it can be. A LED is a one-bit device, so wiring one to a bus is a real mistake and stays flagged.
  - The roadmap had already decided this — "its width stays derived from its net… a probe told the wrong number would quietly show something false" — and the code simply didn't do it. Worth noting as the shape of the miss: the decision was recorded, the reading half was built, and the *declaring* half was left saying the opposite.
  - Tested both ways round, because "declares nothing" must not slide into "declares something wide": a probe on a bus is no fault, and a probe alone on a wire leaves it at one bit. Checked against the probe declaring one bit again.
- [x] **One rule for writing a value, and a base you choose (format v15).** Romain asked for a consistent readout he could set; the request uncovered a fault nobody had named.
  - **There were two formatting rules and they disagreed.** `signal_text` (probe, ports) wrote bare hex above one bit; `format_value` (constant, value panel) wrote prefixed hex above *four* bits and decimal below. So a constant showed `10` where a probe on the same value showed `A`. I had written "building it twice is how the two answers drift" in the very comment that extracted `format_value`, and left `signal_text` beside it unfolded.
  - **The base is the same question everywhere; the prefix is not.** On a symbol, `C` is right — a `0x` on a schematic is noise. In a field you type into, `0xC` is right, because it has to read back. So it is one function with a flag, not two functions.
  - **A global default with a per-component override**, Romain's call when I put the three shapes to him. `NumberBase::Auto` is a *choice not made* rather than a fourth base — the same reasoning `language: Option<Language>` already follows — so changing the setting still moves everything that never asked for something else. `Properties::base` is `Option<NumberBase>`, and *Follow the setting* is offered as a position of its own rather than as the absence of one.
  - **`Auto` resolves to `0`/`1` on a plain wire and hexadecimal on a bus.** Not "hex above four bits, decimal below", which was one of the two old rules: a bus is a bit pattern, and there is no width at which decimal is the better way to read one.
  - **Padding was written, then deliberately taken out again.** Padding to the base's digit count keeps a readout the same size as its value changes, which is worth having — but only once a symbol is *sized* from that number. Before that it turns `FF` into `000000FF` on Romain's 32-bit port and pushes the overflow further out, which is the very thing he reported. The two land together, and `digits()` went with it rather than sitting unused: a method with no caller is how dead code accumulates, which is the rule `canvas_to_screen` already follows.
  - **What is deliberately *not* fixed yet**: a symbol is still one grid box whatever it shows, so a wide value still spills out of it. That is its own roadmap item, and it is a real design question rather than a size — a probe has to stop being a circle, since a circle is only right when what is inside is one character.
- [x] **A readout that fits what it reads.** The other half, done straight after: Romain's 32-bit values were hanging out of both sides of a port and out of a probe.
  - **Two faults, and only one was the size.** The readout was drawn `CENTER_CENTER` on a point eight points inside the body's left edge, so anything longer than a character or two was centred *there* and spilled out of the symbol to the left. Left-aligning it is half the fix, and it was wrong at every width — a two-character value already overhung.
  - **The box is sized from the width and the base, never from the value.** Hexadecimal at 32 bits is always eight characters, so a symbol keeps its size while the simulation runs rather than reflowing and taking its pins with it. Grown in **whole grid steps**, or the pins stop landing on the dots — the rule `BOX_SIZE` was built around, now applied to a box whose width varies (`canvas::snap_up`).
  - **Measured in the real font, at the widest character a readout can hold** — the hex digits plus the letters that stand for a state. Estimating would have been a guess that clips the value the box exists to show, and measuring *the string in front of you* would have made the size follow the value, which is the thing that must not happen. Worked out once a frame and handed to every component rather than sixteen layouts per readout.
  - **`PlacedComponent.readout` is refreshed every frame, not stored and maintained.** A base is a setting that changes without the drawing changing, and a probe's width comes from a net reallocated on every edit — so either would leave a stored number stale. Same bargain as the wire routes. The pre-pass runs before anything asks a component how big it is, since the box is read by the hover test, the marquee and the view framing alike.
  - **A probe stopped being a circle.** A circle is only right while what is inside it is one character; past that the value runs out of both sides. It is a stadium now — a rounded rectangle whose corners are half its height, so at one character it *is* the circle it always was. Rotated by mapping its corners, since a painter will not turn a rounded rectangle and a quarter turn maps it onto another axis-aligned one anyway.
  - **Fixed lengths replaced fractions of the box** in the port, the constant and the source: a lead or an arrowhead written as a fraction stretches with the box, so a 32-bit port would have had a pin a long way from its body and an arrow four times the length of a one-bit port's.
  - **A one-bit component does not move by a pixel**, which the test pins alongside the growth: the margin is chosen so a single character still snaps back to `BOX_SIZE.x`, and every drawing that exists stays exactly as it was.
  - **The sabotage matched nothing the first time**, so the test "passed" against unchanged code — `rustfmt` had split the line being substituted. Caught by checking the substitution landed before believing the run. That is the third time this file records it, and it is always the same lesson: *verify the verification*.
  - **Then it did not work, for two reasons, and the first was my own rule broken.** `rect()` grew — the box you can *click* — while all fourteen draw arms went on building their own `Rect::from_center_size(centre, BOX_SIZE)`. Two definitions of one box, which is exactly what I had written `splitter_rect` to avoid three entries ago, and exactly the fault behind the rotated component that could not be clicked. There is now one `box_rect`, read by the hit area and by every arm. The lesson is not "check the drawing too" — it is that **a value computed in two places will differ**, and the only reliable fix is that there be one place.
  - **The second: fixed lengths swallowed the palette icons.** A symbol is drawn both on the canvas, where its box now grows, and as an icon a good deal smaller than a box — so an inset of ten points and a lead of a grid space left an icon with nothing in the middle. `symbol::fixed(width, fraction, at_most)` is a length that stays proportional below an ordinary box and stops growing above it. At `BOX_SIZE` the cap does not bite at all, which is the point: everything already drawn is drawn exactly as it was, and that is what the test asserts.
  - **The box mismatch is prevented structurally rather than tested.** What is drawn inside a symbol is not observable from a test — there is no widget to query and no geometry handed back — so a test would have had to assert something adjacent and hope. One definition cannot disagree with itself; that is the same trade `Appearance::generated` made against testing the generated box for equality with the drawn one.
  - **And then the ports facing left were still wrong**, which is the third thing left-aligning broke. The anchor is a point in the *symbol's* frame, and a half turn maps it to the far side of the body — so a left-aligned readout ran outwards from there, straight out of the box. The glyphs never turn (text reads left to right on screen whatever the component does), so it is the **alignment** that has to: `readout_align` is `LEFT` at rest, `RIGHT` turned half a circle, and centred on the quarter turns, where the body is tall and narrow and there is no honest horizontal answer.
  - Worth naming the pattern, since it is the same one three times in this entry: **a change that is right in one frame of reference is wrong in the others**, and the frames here are the symbol's own, the screen's, and the palette icon's. The box, the capped lengths and the alignment are one fix each for the same oversight.
  - **Then a quarter turn fell apart entirely, and Romain named the right fix**: *"peut-être que ceux-ci quand on les tourne faudrait-il juste déplacer la pin autour"*. A symbol that is mostly a readout now **keeps its body upright** and moves only its pin — right, bottom, left, top as it turns (`symbol::pin_on_edge`, `keeps_upright`). Its box does not turn either, or a wide symbol would sit in a tall narrow hit area.
    - **Text is never drawn rotated**, so turning the body of a readout leaves a wide value lying across a tall narrow box; turning the box a quarter and keeping the words upright would be worse, since the two would then disagree about which way is up. There is no third option, which is what makes this the answer rather than a compromise.
    - It is **the rule this project already had**: the original generic box "stays axis-aligned; only which edge carries inputs vs. outputs rotates". Romain reached it from what he was looking at; the precedent was in this file the whole time.
    - **The constant needed one thing more**, which Romain spotted: its lead left from the tag's *point* whatever the rotation, so it ran diagonally across the tag on a quarter turn and straight through the body of it on a half. `lead_from` — written for exactly this and then not used here — starts it from the edge facing the pin. And the point now **follows its pin when the pin is to one side**, since the point is what says which way the value leaves; on the quarter turns there is no side to follow, so it stays put. A rect built from two mirrored corners needed `from_two_pos` rather than `from_min_max`: mirroring swaps which corner is which, and an inverted rect reports its sides the wrong way round.
    - **`readout_align` was deleted the same day it was written.** Aligning the text against the rotation was a fix for a symptom of turning the body at all — once the body stays upright there is nothing to compensate, and the honest move was to remove it rather than keep two mechanisms doing one job. Its test went with it, replaced by one on where a pin lands.
